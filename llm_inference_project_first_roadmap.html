Month 1 — Build the benchmark lab
Week 1–2 Set up llama.cpp + run your first model build
Project milestone: A working local inference setup. You can run a 7B model on your RTX 3050 6GB and see tokens generating on screen.

Goal: install llama.cpp from source, download a quantized model, run it, and watch nvidia-smi in a second terminal while it generates. Your first wall will appear here — something won't work. Fix it. That fixing process is the learning.

What to install
llama.cpp — install from source with CUDA support
Follow the CUDA build instructions exactly. The -ngl flag (number of GPU layers) is your first real decision — it controls how many layers offload to your 6GB VRAM vs system RAM. Start with -ngl 20 and observe.
github.com/ggerganov/llama.cpp
Qwen2.5-7B-Instruct Q4_K_M from Hugging Face
Good starting model. Download the GGUF file directly. Q4_K_M fits comfortably in 6GB VRAM at -ngl 33 (all layers on GPU). This is your baseline model for the next 6 months.
huggingface.co
Ollama — install alongside llama.cpp
Use Ollama for quick model swapping during exploration. Use llama.cpp directly for anything you need to measure precisely — Ollama adds overhead you can't control.
ollama.com
Walls you will hit + what to learn when you do
Wall: "what does -ngl actually do and why does changing it affect speed?"
When you hit this → read Tim Dettmers' GPU blog post. Teaches VRAM vs RAM bandwidth difference. 20 minutes. Then come back and experiment with -ngl values.
timdettmers.com
Wall: "why is my 6GB GPU not faster than CPU for some operations?"
When you hit this → read the JAX Scaling Book roofline chapter. Teaches memory-bound vs compute-bound. 30 minutes. This is the core hardware insight for all LLM optimization.
jax-ml.github.io
End of week deliverable
GitHub repo created: llm-inference-lab
README.md: documents your hardware spec (RTX 3050 6GB, 16GB RAM), baseline model choice, and why you chose it
First doc file: 01_hardware_setup.md — what you installed, what -ngl value you settled on, and why
Week 3–4 Build the benchmark script build
Project milestone: A Python script that takes (model, quantization, prompt, n_gpu_layers) as inputs and outputs (tokens/sec, first-token latency, VRAM used, RAM used) as a structured log. This is the instrument you'll use for every experiment from here on.

Goal: build the benchmark lab. Run it across Q4_K_M, Q5_K_M, Q8_0, and F16 on the same model. Record every result. This is your first real dataset.

Tools to use
llama-cpp-python — Python bindings for llama.cpp
Lets you control llama.cpp programmatically. Use Llama() class with verbose=True to capture per-token timing.
github.com/abetlen/llama-cpp-python
psutil + GPUtil for system measurement
psutil reads RAM usage. GPUtil reads VRAM usage. Call both before and after each generation. Log the delta.
Output to CSV or JSON
Every benchmark run appends one row: timestamp, model, quant, prompt_tokens, gen_tokens, tok_per_sec, latency_first_token_ms, vram_mb, ram_mb, n_gpu_layers. You'll thank yourself later.
Walls you will hit + what to learn when you do
Wall: "why does Q4 vs Q8 affect speed, what is actually different?"
When you hit this → read the GGUF format README and Tim Dettmers' 8-bit quantization post. 40 minutes. You'll understand what Q4_K_M is actually doing to the weights. Then re-run your benchmark and the numbers will make sense.
github.com/ggerganov/ggml
Wall: "what is tokens/sec actually measuring and why does prompt length affect it?"
When you hit this → watch 3Blue1Brown Linear Algebra chapters 1–5. The answer is matrix multiplication cost scaling with sequence length. 2 hours. Come back and your benchmark numbers will have a new layer of meaning.
youtube.com/3b1b
End of week deliverable
benchmark.py: working script, committed to repo
results/baseline.csv: Q4 vs Q5 vs Q8 comparison across 3 prompt lengths (short/medium/long)
02_quantization_benchmark.md: your findings documented with decision rationale — "why Q4_K_M is the working default on RTX 3050 6GB" with your own measured numbers as evidence
Month 2 — Understand what you built + go deeper
Week 5–6 Build a tiny GPT + understand what's running on your machine learn
Why now: You've been running a model for a month and hitting walls you can't fully explain. This week you build the thing from scratch so every operation you've been measuring has a concrete code-level anchor.

Goal: build a tiny GPT by hand following Karpathy's video. Understand every tensor shape. Then open your benchmark results and re-read every number with the new mental model.

Primary — do in this order
Karpathy — "The spelled-out intro to neural nets: building micrograd"
Watch first. 2.5 hours, code along. Builds backpropagation from scratch. You need this before the GPT video or the attention mechanism won't make sense.
youtube.com
Karpathy — "Let's build GPT: from scratch, in code, spelled out"
The most important single resource on this roadmap. Code along. Pause constantly. Every tensor shape you understand here maps directly to the model running in your benchmark lab.
youtube.com
Companion reading (open alongside video)
Jay Alammar — "The Illustrated Transformer"
When something in Karpathy's code confuses you, look at Alammar's diagrams. Best visual reference for what each component is doing geometrically.
jalammar.github.io
Walls you will hit + what to learn when you do
Wall: "what is the attention matrix actually computing and why Q × Kᵀ?"
When you hit this → read Lilian Weng's "Attention? Attention!" sections 1–3. 45 minutes. The dot product as similarity measure is linear algebra you already know from Month 1's wall.
lilianweng.github.io
Wall: "why does attention scale as O(n²) and why does that matter for inference speed?"
When you hit this → this is your first direct bridge back to your benchmark lab. Run your benchmark with prompt lengths 128, 512, 1024, 2048 and plot the latency. The O(n²) curve will appear in your own data.
End of week deliverable
03_transformer_internals.md: explain in your own words — what is attention, what is the KV cache, why does context length hurt performance. Documented with your benchmark data showing the O(n²) effect.

Week 7–8 Build a KV cache memory profiler build
Project milestone: A tool that visualizes KV cache memory growth as context length increases on your specific hardware. This is original work — it targets the 6GB VRAM constraint specifically and produces data nobody else has published for this exact configuration.

Goal: extend your benchmark script to track KV cache memory consumption at context lengths 128, 256, 512, 1024, 2048, 4096. Plot the growth curve. Answer: at what context length does your 6GB VRAM run out of KV cache headroom?

What to learn when you hit walls here
Wall: "what exactly is stored in the KV cache and how do I calculate its size?"
When you hit this → read Lilian Weng's inference optimization post. The KV cache memory formula is: 2 × n_layers × n_heads × head_dim × context_length × bytes_per_element. Work through this formula with your model's actual parameters. It's just arithmetic once you know the shape.
lilianweng.github.io
End of week deliverable
kv_cache_profiler.py: committed to repo
results/kv_cache_growth.csv: memory measurements at each context length
04_kv_cache_analysis.md: your findings — "at what context length does KV cache become the bottleneck on 6GB VRAM, and what does that mean for real use cases?" This doc has original measured data. Nobody else has this exact chart for RTX 3050 6GB.
Month 3 — Read and implement one paper
Week 9 Learn how to read a paper + read FlashAttention paper
Why now: Your KV cache profiler showed you exactly where memory is being wasted. FlashAttention is the most important optimization that addresses memory-bound attention. You now have the context to understand why it matters.

Goal: learn the three-pass paper reading method, apply it to FlashAttention, and understand why tiling fixes the memory problem your profiler revealed.

Read in this order
S. Keshav — "How to Read a Paper" (3-page PDF)
Read this first, takes 15 minutes. Pass 1 = title/abstract/headings/conclusion. Pass 2 = figures and main content. Pass 3 = deep read. Use this method for every paper from now on.
sigcomm.org
ELI5 FlashAttention — Aleksa Gordić on Medium
Read this before the paper. Explains tiling and SRAM vs HBM in plain English. After reading, the paper's Section 3 will make sense on first pass.
medium.com
FlashAttention paper — Dao et al. 2022
Pass 1 + Pass 2 only. Focus on Section 2 (background — this connects directly to your roofline wall from Week 1) and Section 3 (algorithm). Skip CUDA kernel implementation.
arxiv.org/abs/2205.14135
End of week deliverable
05_flashattention_notes.md: your paper notes in the decision rationale format — what problem it solves, what the core insight is, what it trades off, what breaks if you remove it. Interview questions at the end.
Week 10–12 Implement SnapKV and benchmark it implement
Project milestone: A working implementation of SnapKV — KV cache compression by dropping unimportant keys — benchmarked against your baseline using your Week 3–4 benchmark lab. This is Project #1.

Goal: implement SnapKV as a hook on top of your model, run your benchmark on original vs SnapKV, measure the tradeoff between KV cache memory saved and output quality lost. Three weeks because implementation always takes longer than expected.

Paper + implementation reference
SnapKV paper — Li et al. 2024
Pass 1 + 2 first. The core idea is simple: cluster keys by attention score, keep only the top-K most attended positions. Section 3 is the implementation spec.
arxiv.org/abs/2404.14469
SnapKV reference implementation on GitHub
Read the reference code after reading the paper — not before. Understand the algorithm first, then see how it was implemented. Search "SnapKV implementation github".
github.com/FasterDecoding/SnapKV
Quality measurement tools
llama.cpp perplexity tool (built in)
Run: ./perplexity -m model.gguf -f wikitext-2-raw/wiki.test.raw. Lower = better. Compare baseline vs SnapKV. This is your quality metric.
Walls you will hit + what to learn when you do
Wall: "how do I hook into the attention layer to intercept the KV cache?"
When you hit this → read the Hugging Face transformers source for the attention module. The generate() function has a past_key_values argument that is the KV cache. Modifying it is where your implementation lives.
huggingface.co/docs
Wall: "my perplexity is much worse than the paper reports — why?"
When you hit this → check your K value (how many keys you're keeping). The paper uses task-specific tuning. On your hardware, sweep K from 16 to 256 and plot perplexity vs memory saved. That sweep IS your research contribution — the paper didn't do it on 6GB VRAM.
End of week deliverable — Project #1 complete
snapkv/: implementation committed to repo
results/snapkv_benchmark.csv: memory saved vs perplexity delta at K=16, 32, 64, 128, 256
06_snapkv_implementation.md: full decision rationale doc — what you implemented, why SnapKV specifically, what the K sweep showed on RTX 3050 6GB, what the optimal K value is for your hardware, what breaks if K is too low or too high. Interview questions at the end.
Month 4 — Read the other key papers + deepen the lab
Week 13–14 Read PagedAttention + speculative decoding papers
Why now: Your SnapKV implementation gave you deep KV cache understanding. PagedAttention and speculative decoding are the two other foundational optimizations. Reading them now — after implementation experience — means you'll understand the tradeoffs at a level you couldn't have before Month 3.

Goal: read both papers using the three-pass method. Understand the core insight of each. Crucially — identify what each paper's approach costs on consumer hardware specifically, not just at datacenter scale.

PagedAttention
vLLM blog post first, then the paper
Blog explains the memory fragmentation problem visually. Paper Section 3 (Figure 2) is the core insight. Focus on why this matters for your 6GB VRAM — fragmentation wastes headroom you can't afford.
blog.vllm.ai
Speculative decoding
Lilian Weng inference optimization post (speculative decoding section)
More accessible than the original paper. Read this first. Key question to answer: why does speculative decoding require a second draft model, and why is that a problem on 6GB VRAM specifically?
lilianweng.github.io
Speculative Decoding paper — Leviathan et al. 2023
Pass 1 + 2. Section 2.1 algorithm and the acceptance criterion in Theorem 1 are the core. The draft model memory cost is your hardware-specific insight — a second model doesn't fit in 6GB alongside your primary model.
arxiv.org/abs/2211.17192
End of week deliverable
07_pagedattention_notes.md and 08_speculative_decoding_notes.md: same decision rationale format as your other docs. For each: what problem it solves, core insight, hardware-specific tradeoff on 6GB VRAM, interview questions.
Key insight to document: speculative decoding requires a draft model that competes for your 6GB VRAM. This constraint is what makes the 6GB consumer hardware problem different from datacenter inference. That gap is where your novel idea will come from.
Week 15–16 Read llama.cpp source code + extend the benchmark lab build
Project milestone: Extend your benchmark lab to test context length vs throughput tradeoffs, and add a speculative decoding comparison using llama.cpp's built-in support for it.

Goal: read the llama.cpp inference loop and KV cache implementation. Understand exactly how the tool you've been using for 4 months works internally. Then add speculative decoding benchmarks to your lab — llama.cpp supports it natively with -md (draft model) flag.

Where to start in llama.cpp source
Start with the sampling loop in llama.cpp, then trace kv_cache references
Read the token generation loop first — it's simpler than the full model. Then use GitHub search for "kv_cache" to find every place it's managed. The PR comments on key commits are more educational than the code itself.
github.com/ggerganov/llama.cpp
Speculative decoding experiment
Run llama.cpp speculative decoding with a tiny draft model
Use a 1B model (e.g. Qwen2.5-1B) as draft, 7B as target. The 1B + 7B together need to fit in your 6GB VRAM — they won't at full precision, but Q2 + Q4 might. Measure whether speculative decoding actually helps on your hardware. The result — whatever it is — belongs in your documentation.
End of week deliverable
results/speculative_decoding_benchmark.csv: tokens/sec and quality comparison with and without speculative decoding on your hardware
09_speculative_decoding_on_6gb_vram.md: your original finding — does speculative decoding help or hurt on 6GB VRAM? Why? This is a genuinely useful data point for r/LocalLLaMA that doesn't exist in published literature.
Month 5 — Find and prototype your novel idea
Week 17–18 Idea journal + identify your research question research
Your data will give you the idea. By now you have 4 months of benchmark results, a SnapKV implementation, and a speculative decoding experiment that revealed something about 6GB VRAM specifically. The novel idea comes from the frustration in that data, not from brainstorming.

Goal: review all your benchmark results and documentation. Find the one thing that surprised you most. That surprise is your research question. Write it down precisely.

Questions to ask your existing data
Where is performance worse than expected given the roofline model?
If your measured throughput is significantly below the theoretical maximum given your bandwidth, something is inefficient. That gap is a research question.
What does the 6GB VRAM constraint uniquely break vs datacenter GPUs?
Speculative decoding needs two models. PagedAttention assumes more headroom. What optimization assumes a resource you don't have? That assumption is a target.
In your SnapKV K-sweep, was there a non-obvious sweet spot?
If the perplexity vs memory curve had an unexpected shape for your hardware — that's a finding. Could a dynamic K value (adapting per layer or per token) do better than a fixed K?
Arxiv search before building
Search your idea on arxiv before implementing
Search "LLM inference consumer GPU optimization", "dynamic KV cache", "mixed precision inference 6GB". If your idea already exists, read it — maybe you can extend it for your specific constraint.
arxiv.org
End of week deliverable
10_research_question.md: one page. The problem you identified, evidence from your benchmark data that it's real, your hypothesis for a fix, and why existing approaches don't solve it. This document is the most important thing you will write in the entire 6 months.
Week 19–20 Rapid prototype + measure novel
Project milestone: A working prototype of your novel idea, however rough. Measured against your baseline. Most ideas will show weak or no improvement. That result is not failure — it's data.

Goal: build the fastest possible version of your idea that you can measure. Don't optimize the prototype — just get it running and benchmark it immediately. The measurement tells you whether to continue or pivot.

If the prototype shows no improvement
Document why it failed — this is research
A failed hypothesis with a clear explanation of why it failed is a legitimate research contribution. Write exactly why the approach didn't work, what assumption was wrong, and what you'd try next. That analysis is Month 6's technical report.
If the prototype shows improvement
Verify it's real — run the benchmark 5 times and average
Single-run improvements are often noise. Run your benchmark 5 times with and without the change, average the results, and check variance. Only proceed to Month 6 full implementation if the improvement holds across runs.
Community gut-check: Post your research question (not your implementation) to r/LocalLLaMA with your benchmark data. Ask if anyone has seen this behavior. The community response tells you whether you're onto something real or missing prior work. You'll get feedback within 24 hours.
Month 6 — Full implementation + technical report
Week 21–23 Full implementation + comprehensive benchmarking novel
Project milestone: The final, clean implementation of your novel idea (or your best SnapKV extension), with comprehensive benchmarks comparing against baseline and existing methods. This is the artifact that goes on your resume.

Goal: clean up your prototype, run comprehensive benchmarks (speed, memory, quality), and compare against at least two baselines — your original unmodified model and your SnapKV implementation.

Week 24 Write the technical report deliverable
Final deliverable: A structured technical report that someone else can read, reproduce, and build on. This — alongside your BiteCast documentation — is what you show in interviews.

Goal: write the technical report in the same decision rationale format you used for BiteCast. Be honest about what failed. The failures are what interviewers remember.

Structure
Problem → Hardware context → Background → Hypothesis → Method → Benchmarks → Results → What failed → What surprised me → Future work
The "Hardware context" section is unique to your project — explicitly state that this work targets the 6GB VRAM consumer hardware constraint that datacenter research ignores. That framing makes your contribution specific and defensible.
The one sentence that makes your resume
"Implemented and benchmarked LLM inference optimization on consumer hardware (RTX 3050 6GB), achieving X% KV cache reduction via SnapKV with Y perplexity delta, and identified Z as an underexplored optimization target for the sub-8GB VRAM constraint."
Fill in X, Y, Z with your actual numbers. That sentence, if true and measurable, is worth more than any course certificate.
Post it publicly. Publish your benchmark results to r/LocalLLaMA with a link to your GitHub repo. The community will validate your methodology, point out anything you missed, and potentially cite your numbers. Real community engagement on your work is the strongest possible validation — better than any grade.
